# Safety Net — оценка перед рефакторингом

## Цель

Рефакторинг без safety net — это лотерея. Прежде чем менять структуру кода, нужно убедиться, что регрессию заметят. Этот модуль помогает оценить, достаточен ли существующий safety net, и что делать, если нет.

## Что проверять

### 1. Автоматические тесты

- Какие типы тестов есть: unit, integration, e2e, contract, snapshot?
- Прогоняются ли они локально без ошибок прямо сейчас? Зафиксируй baseline.
- Какое покрытие у затрагиваемого модуля? Запусти coverage-прогон:
  ```
  # Vitest/Jest
  npx --no-install vitest run --coverage
  npx --no-install jest --coverage

  # Python
  pytest --cov=<module> --cov-report=term-missing
  ```
- Проценты покрытия — входные данные для риск-матрицы (см. ниже), а не самостоятельный вердикт. Ориентиры: покрытие строк < 70% или ветвлений < 60% по затрагиваемой области — повод оценить риск внимательнее, не автоматический запрет.

### 2. Характер тестов

Покрытие в процентах само по себе ничего не значит. Проверь:

- Тесты проверяют **поведение** или **реализацию**? Тесты на реализацию (mock-heavy, проверка вызовов приватных методов) ломаются при рефакторинге, хотя поведение не изменилось. Это антипаттерн.
- Есть ли тесты, которые пропущены / заскипаны (`.skip`, `xit`, `@pytest.mark.skip`)?
- Запускаются ли тесты в CI на каждый PR?

### 3. Типизация

Для TS:

- Проходит ли `pnpm tsc --noEmit` без ошибок?
- Какой уровень strict-настроек? Включены ли: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`?
- Сколько `any` в кодовой базе? `grep -rn ": any" --include="*.ts" --include="*.tsx" | wc -l`
- Сколько `as` type assertions? `grep -rn " as [A-Z]" --include="*.ts" --include="*.tsx" | wc -l`

Для Python:

- Есть ли mypy / pyright? Проходит ли `mypy --strict`?

### 4. Линтинг

- Biome / ESLint / oxlint / Ruff настроены? Fail-on-warning?
- Какие правила отключены? Часто отключают именно те правила, которые ловят проблемные конструкции.
- Есть ли **type-aware** правила (`no-floating-promises`, `no-unsafe-*`)? Это сильная часть safety net — они ловят реальные баги. Варианты: typescript-eslint (эталон), Biome 2 (Biotype, ~75-85% покрытия правил без tsc), oxlint `--type-aware` (tsgolint поверх tsgo).

### 5. Mutation testing (бонус)

Если настроен Stryker (JS/TS) или mutmut (Python) — это золотой стандарт оценки качества тестов. Mutation score < 70% = тесты пропускают много регрессий.

## Что делать, если safety net слабый

### Сценарий A: legacy-код без тестов

Используй **characterization tests** (Michael Feathers, Emily Bache):

1. Возьми целевую функцию / модуль.
2. Сгенерируй репрезентативный набор входов (реальные данные из production-логов, граничные случаи, случайные генерации через property-based).
3. Запусти код, зафиксируй выходы.
4. Сохрани пары (вход, выход) как golden master / approval-файлы.
5. Тест = пропустить вход через код и сравнить с golden.

Библиотеки:

- **JS/TS**: `jest-image-snapshot`, `ava snapshot`, `vitest toMatchSnapshot`, `approvaltests-js`
- **Python**: `pytest --snapshot`, `approvaltests`
- Для любого языка: просто сохраняй JSON/text fixtures и сравнивай.

Characterization tests фиксируют текущее поведение «как есть» — даже с багами. Это нормально: цель — не изменить поведение при рефакторинге. Если баги известны — их исправляют отдельным коммитом после рефакторинга.

### Сценарий A2: работающий сервис (HTTP/RPC) без юнит-тестов

Для сервиса golden master строится на уровне API, не залезая в код:

1. Собери набор эталонных запросов: реальные из логов + граничные случаи.
2. Зафиксируй ответы или их **инварианты** (статус, ключевые поля, число результатов) как эталон.
3. Оформи как smoke-тест, который гоняется против dev-инстанса (или копии прода) до и после рефакторинга — локально или в CI по dispatch.
4. Для недетерминированных ответов (ранжирование, timestamps, generated id) сравнивай инварианты, а не побайтовое равенство. Пороговые проверки формулируй как рост-инварианты (`>=`), не точные (`==`), иначе следующее обновление данных сломает тест.

Это полноценный safety net для рефакторинга внутренностей сервиса: он проверяет наблюдаемое поведение ровно там, где его видят потребители.

### Сценарий B: есть тесты, но mock-heavy

Тесты, которые проверяют «был ли вызван метод X с аргументами Y», ломаются при любом рефакторинге. Перед рефакторингом:

1. Замени mock-тесты на тесты через публичный API модуля.
2. Используй integration-тесты с реальными зависимостями где возможно (in-memory БД, testcontainers).
3. Mock оставь только для внешних систем (HTTP, почта, платежи).

### Сценарий C: нет типов

Прежде чем рефакторить нетипизированный код:

1. Проверь затрагиваемый модуль строгой проверкой, не меняя конфиг проекта: для TS — отдельный `tsconfig.refactor.json` (`extends` от основного + `strict: true` + узкий `include`), запуск `tsc -p tsconfig.refactor.json --noEmit`; для Python — `mypy --strict <модуль>` точечно. Встроенной per-file директивы строгости у tsc НЕТ (`// @ts-strict` — это сторонний typescript-strict-plugin, его без согласия не добавляем); файл-конфиг для проверки можно держать незакоммиченным.
2. Добавь типы на публичные границы функций (это уже правка кода — только в режиме execute и в scope).
3. Это само по себе вскроет часть багов и даст намного больше уверенности.

### Сценарий D: есть CI, но проверки слабые

Добавь gates в pipeline:

- `tsc --noEmit` — блокирующий.
- `biome check` / `eslint --max-warnings 0` — блокирующий.
- Тесты — блокирующие.
- Coverage — не регрессирует (сравнение с main).
- Bundle size — не регрессирует неожиданно.

## Риск-матрица: что считать достаточным safety net

Достаточность страховки определяется ПАРОЙ «изменение × наличные проверки», а не одним числом покрытия:

| Планируемое изменение | Достаточный safety net |
|---|---|
| Rename / extract function / move при строгом тайпчекере (strict TS, mypy strict) | Типы + существующие тесты — даже при низком coverage: компилятор ловит основной класс ошибок |
| Механический codemod | Dry-run с балансом счётчиков + компиляция/типы + выборочное ревью diff + тесты |
| Перестройка условий и ветвлений | Branch coverage целевой области ЛИБО characterization tests на входы, бьющие по этим ветвям |
| Деньги, биллинг, квоты, доступы | Characterization + существующие гард-тесты + человеческое ревью; высокий line coverage сам по себе НЕ достаточен |
| Код без типов и без тестов | Сначала характеризация (сценарии A/A2 выше), потом рефакторинг |
| Изменение с необратимыми эффектами (миграции БД, форматы хранения) | Вне рамок чистого рефакторинга — отдельное решение пользователя |

Контрольный список перед execute — это сбор фактов для матрицы, не механический гейт:

```
[ ] Baseline зафиксирован: тесты прогнаны, результат записан (в т.ч. список заведомо красных)
[ ] Известно, гоняются ли тесты в CI и какой командой (workflow — источник правды)
[ ] Coverage затрагиваемой области измерен (если инструмент уже настроен в проекте)
[ ] tsc --noEmit / mypy — состояние известно (если TS/Python с типами)
[ ] Линтер — состояние известно
[ ] Worktree чистый; план отката = git restore/revert СВОИХ правок (не reset --hard)
[ ] Согласована цель и scope (не «улучшу как получится»)
```

Решение «строить safety net или рефакторить сейчас» принимай по матрице и объясняй в отчёте, какая строка применена и почему.
